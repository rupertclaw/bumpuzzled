## 1. What this project is

A grid-routing brain-teaser puzzle game. Single-page PWA. **No server, no build step, no dependencies, no framework** — plain HTML/CSS/JS + a service worker. The entire game ships in ~20KB of hand-written code.

It is a tribute to **Puzzle Crusher** (studio: Gamescan, incubated by Seascape Network), an iOS/Android web3 puzzle-platformer active ~2023-2024. That game is now dead: Play Store listing 404s, App Store lookup returns nothing, the puzzlecrusher.com domain no longer resolves, and the studio's X/Twitter went quiet in 2024. Notably its web3/tokens/NFT features never actually shipped — the playable game was already plain web2 gameplay underneath.

What was worth preserving (per the player who commissioned this): **the brain-teaser feel and the progressive difficulty curve**. What was deliberately dropped: web3 mechanics, hearts/lives punishment economy, building-upgrade meta layer. Undo replaces lives. Death is a recoverable state, not a cost.

Current scope: **prototype** — 6 levels proving the core loop. Roadmap discussed with the owner (Graeme):
1. More levels (12-16 total)
2. **Level editor + share-a-level-via-URL** (the feature Puzzle Crusher promised and never shipped; levels would be encoded into the URL itself, still no server)
3. Visual polish pass

Owner preferences that constrain design decisions:
- Web2 only. No API keys in client code ever. No server, no database. Everything local.
- PWA-first, primary usage is mobile (installs to home screen, must work offline).
- Simple/universal UX beats platform-specific branching.
- This is a personal/hobby project under the `rupertclaw` GitHub account. There is also a `MaplePulse` account used for a different project (Regional Pulse News) — do not mix them up. Tile Rush belongs to `rupertclaw` only.

## 3. The game, precisely

### 3.1 Board

2D grid of characters, rendered from `LEVELS[i].grid` (array of strings). Player at a position; four inputs U/D/L/R (up/down/left/right). One input = one move.

### 3.2 Tiles (canonical character set)

| Char | Name | Behavior |
|---|---|---|
| `#` | Wall | Blocks everything: walking, spring launches, jump landings. |
| `.` | Floor | Walk 1 cell. |
| `P` | Player spawn | Exactly one per level. Acts as floor. |
| `H` | Hole | Walking in = DEATH (recoverable via Undo/Restart — see 3.5). Cannot be landed on from jumps/teleports. Springs fly over runs of H. |
| `J` | Jump pad | Walkable. If standing ON J and pressing toward an adjacent H: leap over it, landing exactly 2 cells away in that direction. Landing must be floor-like (not `#`, not `H`, not closed `B` = out of bounds also blocks). If the adjacent tile isn't H, J acts as normal floor. |
| `S` | Spring | Walkable. If standing ON S and pressing ANY direction: launch straight that way, skipping every H in the path, landing on the first non-H tile. If that tile is `#` or closed `B`, the launch is blocked (no move). |
| `T` | Trigger | Walkable. **Landing** on T sets `bridgesOpen = true` for the rest of the level visit. |
| `B` | Bridge | Closed B blocks exactly like `#`. Open B is floor. Opened by T. |
| `1`/`2` | Teleport pair | Walkable. **Landing** on one instantly warps you to the other. Arrival effects at the partner apply exactly once (so warping onto E wins; warping onto T opens bridges; you cannot warp-loop). `3`/`4` would work identically (second pair, reserved). |
| `E` | Exit | Walkable. **Arriving** on E wins the level. |

### 3.3 Movement engine, exactly (mirror of code)

`step(grid, r, c, bridgesOpen, dir)` returns one of:
- `null` → blocked, state unchanged (game shows "Blocked.")
- `{fall: true}` → stepped into a hole
- `{r, c, bridgesOpen, won}` → landed (possibly after teleport/warp) at (r,c), with possibly-updated bridgesOpen, won=true if tile was E

Order of operations inside `step`:
1. If standing on `S`: ray-launch (skip all H, land first landable or blocked).
2. Else compute target (r+dr, c+dc):
   - Target is `H`: if standing on `J` → leap to 2-ahead (must be landable, else no move). Else → `{fall:true}`.
   - Target is `#` or closed `B` → `null`.
   - Else → land().
3. `land(r, c, br)`: if tile is E → won. If T → br=true. If teleport digit → find partner cell, warp there (partner's tile does NOT re-trigger its own teleport; other effects like E/T DO apply at the partner — check `land` source for the exact one-pass behavior).

Important subtlety (tested and locked): the leap/launch checks the CURRENT cell's tile (J or S), not the target's.

### 3.4 State model

`solve`-state = `(row, col, bridgesOpen:boolean)`. That's the entire game state. This is what the BFS searches; the JS game adds only UI state (history stack, move count, progress flags).

### 3.5 Lives/undo model

No lives. Death (H) or any state is fully recoverable:
- **Undo** pops the history stack (which snapshots pos+bridgesOpen per move, including a death flag).
- **Restart** reloads the current level.
- Death does NOT increment a counter, lock progress, or cost anything. Design decision, keep it.

### 3.6 Progress model (localStorage)

Single localStorage key `tilerush`, JSON:
- `best<N>` → best (fewest) moves achieved on level N (N is 1-indexed), only written when beaten
- `unlocked` → highest level index reached (0-indexed), used to resume where the player left off

Clearing site data resets everything. No accounts, no sync — by design (privacy-first, no server).

## 4. Verification — THE critical workflow

Three copies of level/solution data must always agree:

1. `sim.py` `LEVELS` (Python) — used by BFS
2. `game-core.js` `LEVELS` (JS arrays) + `SOLUTIONS` (par strings)
3. `solutions.json` (generated)

`python3 verify.py` then enforces:
- Fresh BFS solve of every sim.py level == solutions.json
- game-core.js grids == sim.py grids (structural JSON comparison via node)
- game-core.js SOLUTIONS == solutions.json
- Every solution, replayed move-by-move through the real `step()` engine in node, reaches WON
- Exits 0 only if all pass; prints `*** DRIFT DETECTED — DO NOT SHIP ***` otherwise

`index.html` also self-verifies at page load (same replay logic in the browser; sets `<title>` to `Tile Rush (VERIFY FAIL)` on failure). So a broken deploy announces itself.

**Contributor rule: any change to LEVELS, SOLUTIONS, or step()/land() logic → run `python3 sim.py && python3 verify.py`. No exceptions.** The whole reason the solver exists is that hand-authored levels are how you accidentally ship an unsolvable puzzle (this actually bit during development — a double-hole `HH` in level 5's draft made it unsolvable and only the BFS caught it).

Adding a level, full checklist:
1. Append to `sim.py` `LEVELS` (as dict entry, next integer)
2. Run `python3 sim.py` — must print `solvable, par=N path=...` (if UNSOLVABLE, redesign the grid; don't weaken the solver)
3. Copy the EXACT same grid strings + name into `game-core.js` `LEVELS` array
4. Copy the par path string into `game-core.js` `SOLUTIONS` as `N: "UDLR..."`
5. Run `python3 verify.py` → must be ALL CHECKS PASS
6. Bump `sw.js` CACHE version
7. Deploy (see §6), then hard-verify the live site

Requirements for a valid grid: rectangular (every row same length — write a width assert, see §8 Pitfalls), exactly one `P`, exactly one `E`, BFS-solvable. Row width gotcha: `#PJHJH.E#` is NINE characters, not eight. Count programmatically; eyeballing is how the `#` and `E#` mix happened twice.

Level design guidance so far (what the first 6 establish):
- L1 teaches walking + walls. L2 teaches springs-over-holes. L3 teaches trigger/bridge + backtracking. L4 teaches teleporters (one-way pocket). L5 chains jump pads (4-move speedrun-level). L6 combines spring + trigger + holes.
- Each level: introduce mechanic, then next level assumes mastery. Par is the skill target; BFS par = perfect play, so human par is usually BFS+20-50%.

## 5. Code architecture rules

- **`game-core.js` stays pure/DOM-free.** No `document`, no `window`, no `localStorage` in it. This is what allows node-side verification. If you need UI, put it in index.html.
- No dependencies, no bundler, no transpile. Plain ES6 that old-ish mobile Safari handles. `browser` skill/Playwright not needed for dev.
- All UI in index.html: grid rendered as `div.cell` elements with CSS classes per tile type; player re-renders on every move (cheap; boards are tiny).
- Input paths: on-screen D-pad buttons, swipe (touchstart/touchend delta), keyboard (arrows + WASD, plus `z`=undo, `r`=restart). All three call the same `move(dir)`.
- Resize handling exists (`resizeBoard()` computes cell size from viewport); call it on level load too (it is).

## 6. Deployment

GitHub Pages from `main` root. Push to `main` → live in ~60s.

Verify a deploy like this (do not skip):
```bash
curl -s https://rupertclaw.github.io/tile-rush/ | grep -F TILE
curl -s https://rupertclaw.github.io/tile-rush/game-core.js | grep -F "function step"
```
And ideally open the live site with JS enabled once after big changes to watch for the boot-time `VERIFY FAIL` title.

**Gotchas:**
- Pages caches aggressively. After deploy, if something looks stale, hard-refresh or check `game-core.js` byte length against local.
- The service worker makes this worse for returning players: **bump `CACHE = "tilerush-vN"` in sw.js whenever any shipped file changes.** Otherwise returning users play stale code until the SW refreshes.
- Pushing to `main` deploys straight to production (no staging branch on this repo — acceptable for scale, but if you want a safety net, a `gh-pages`-style preview via Vercel or a `staging` branch + Pages config change are options).

No secrets, no tokens, no env vars anywhere in this repo — that's a design invariant, keep it that way. If a future feature (e.g. analytics) seems to need a key, raise it with the owner first; the standing preference is no client-side secrets, and no server.

## 8. Known pitfalls (read before your first contribution)

1. **Cell-counting by eye.** Already bit twice. Assert row widths in sim.py (`assert all(len(row)==w)`) — there's already an assertion there, keep it.
2. **Forgetting the third copy.** Adding a level means sim.py + game-core.js LEVELS + game-core.js SOLUTIONS. verify.py catches all three, but don't rely on it — check your own work first.
3. **sw.js version constant.** Silent staleness for returning players if forgotten. The deploy can be "correct" server-side and still wrong for users.
4. **Teleport arrival semantics.** Only re-check partner effects once. If you touch `land()`, re-run verify + manually replay L4 (the teleport level) in the browser.
5. **bridgeOpen state in undo history.** Each history entry snapshots `{pos, bridgesOpen, death}`. If you add level state (e.g. one-shot triggers, keys, buttons), it must join the snapshot AND the BFS state tuple in sim.py, or solver and game will disagree — verify.py's structural checks won't catch state-machine drift, only the replay will (partially). When in doubt, extend verify.py first.
6. **index.html self-verification** reads SOLUTIONS from game-core.js at load. If you rename/move SOLUTIONS, update both files.
